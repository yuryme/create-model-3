## 1. Бизнес-задача

Этапы 1a и 1b уже дают операционное ядро хлебозавода: заявки клиентов, производственные задания, рецептуры, поступление сырья, инвентаризацию, выпуск продукции, количественные остатки сырья и готовой продукции, а также возникновение долга поставщику при поступлении сырья. Но цикл ещё не закрыт: готовую продукцию нельзя отгрузить клиенту, долг клиента не возникает, оплату клиента и оплату поставщику нельзя отразить, общий денежный результат не виден.

Этап 1c закрывает эту цепочку минимальным управленческим контуром. Кладовщик или менеджер оформляет отгрузку готовой продукции клиенту. Система списывает готовую продукцию со склада и увеличивает дебиторскую задолженность клиента. Финансист фиксирует поступление денег от клиента, что увеличивает общий денежный остаток и уменьшает дебиторку. Финансист также фиксирует оплату поставщику, что уменьшает общий денежный остаток и кредиторку поставщика, возникшую на 1b.

Руководитель должен получить три итоговых взгляда: дебиторка клиентов, кредиторка поставщиков и движение денег. Контур остаётся минимальным: без договоров, авансов как отдельной сущности, кассы/банка, статей ДДС, себестоимости, P&L и закрытия месяца.

## 2. Архитектурный подход

### 2.1. Предполагаемые метаобъекты

| Действие | Вид | Имя | Назначение |
|---|---|---|---|
| CREATE | records | `customer_settlements` | Движения дебиторской задолженности клиентов по организации и клиенту. |
| CREATE | records | `money_balance` | Движения общего денежного остатка по организации. |
| MODIFY | records | `finished_goods_movement` | Existing регистр 1b; отгрузка добавляет расход готовой продукции без изменения состава регистра. |
| MODIFY | records | `supplier_debt_movement` | Existing регистр 1b; оплата поставщику добавляет погашение кредиторки без изменения состава регистра. |
| MODIFY | register | `price_list` | Existing регистр 1a; команда отгрузки читает актуальную цену, состав регистра не меняется. |
| CREATE | operation | `shipment` | Документ отгрузки готовой продукции клиенту. |
| CREATE | operation | `payment_in` | Документ поступления денег от клиента. |
| CREATE | operation | `payment_out` | Документ оплаты поставщику. |
| CREATE | data_view | `customer_debt_report` | Отчёт по дебиторской задолженности клиентов. |
| CREATE | data_view | `supplier_debt_report` | Отчёт по кредиторской задолженности поставщикам. |
| CREATE | data_view | `money_flow_report` | Отчёт по денежным движениям и общему итогу за период. |

`MODIFY` для existing объектов означает только новое использование в проведении или чтении. Прямое изменение JSON-файлов `finished_goods_movement`, `supplier_debt_movement` и `price_list` не требуется, если фактический metadata-контракт 1a/1b совпадает с уже утверждёнными ТЗ.

### 2.2. Ключевые связи

- `operation/shipment` ссылается на `catalog/company`, `catalog/counterparty` как клиента, `catalog/warehouse` как склад готовой продукции и `catalog/nomenclature` в строках продукции.
- `operation/shipment` читает `register/price_list`, чтобы подобрать актуальную цену продукции на дату отгрузки.
- `operation/shipment` читает `records/finished_goods_movement`, чтобы показать и проверить остаток готовой продукции перед отгрузкой.
- `operation/shipment` пишет расход в existing `records/finished_goods_movement` и рост долга клиента в новый `records/customer_settlements`.
- `operation/payment_in` пишет приход денег в `records/money_balance` и погашение дебиторки в `records/customer_settlements`.
- `operation/payment_out` пишет расход денег в `records/money_balance` и погашение кредиторки в existing `records/supplier_debt_movement`.
- `data_view/customer_debt_report` читает `records/customer_settlements`.
- `data_view/supplier_debt_report` читает `records/supplier_debt_movement`.
- `data_view/money_flow_report` читает `records/money_balance`.

### 2.3. Ключевые алгоритмы

- **Подготовка отгрузки.** Перед проведением пользователь запускает команду подготовки отгрузки. Команда по строкам продукции подбирает актуальную цену из `price_list` как последнюю активную цену с датой начала действия не позже даты отгрузки, рассчитывает сумму строки и показывает остаток готовой продукции по `finished_goods_movement`. Если цены нет или остатка недостаточно, команда возвращает понятную ошибку.
- **Проведение отгрузки.** Отгрузка списывает количество готовой продукции и создаёт дебиторку клиента на сумму строк. Склад ГП остаётся количественным, без себестоимости.
- **Поступление денег.** Входящий платёж увеличивает общий денежный остаток и уменьшает дебиторку клиента. Разнесение по конкретным отгрузкам не выполняется.
- **Оплата поставщику.** Исходящий платёж уменьшает общий денежный остаток и уменьшает кредиторку поставщика. Разнесение по конкретным поступлениям сырья не выполняется.
- **Отчёты.** Дебиторка и кредиторка считаются как сальдо движений по контрагенту на дату. Движение денег выводится за период с итогом по сумме.

### 2.4. Принципиальные компромиссы и доказательная база

- **Расчёты по контрагенту, без договоров и авансов.** Это продолжает компромисс первой очереди из `sp-001-bakery-stage1-design.md`, раздел 2.4: взаиморасчёты ведутся по контрагенту, договоры и авансы — развитие следующих очередей.
- **Деньги одним абстрактным счётом.** Это продолжает решение из `sp-001-bakery-stage1-design.md`, раздел 2.4: для первой очереди достаточно общего денежного остатка без кассы, банка и статей ДДС.
- **Проведение документов через recordsSettings.** Возможность подтверждена документацией `basys-docs/ru/metadata/recordsCreation.md`, разделы «Общая схема работы», «Настройка создания записей», «Источники данных для записей». На этом основаны движения `shipment`, `payment_in`, `payment_out` в регистры записей.
- **Команда подготовки отгрузки.** Программируемые команды подтверждены `basys-docs/ru/commands/programmableCommands.md`, раздел «Контекст выполнения команды». QueryBuilder-запросы к данным и группировки подтверждены `basys-docs/ru/calculations/queryBuilder.md`, разделы `from`, `select`, `where`, `groupBy`, `parameter`.
- **Отчёты как data_view.** Панели данных и табличные отчёты подтверждены `basys-docs/ru/reporting/dataView.md`, разделы «Панели данных», «Таблица», «Фильтры».
- **Никаких неподтверждённых save-hooks.** Контроль остатка готовой продукции проектируется как командная проверка перед проведением. Если позже будет нужен автоматический запрет сохранения без запуска команды, это требует отдельного подтверждения capability и не закладывается как обязательная основа 1c.

## 3. Рассмотренные альтернативы

- **Дебиторка только отчётом vs отдельный `records/customer_settlements`.** Выбран отдельный регистр движений, потому что payment_in должен погашать долг клиента тем же механизмом, которым shipment его создаёт. Отчёт без регистра не дал бы устойчивого источника для оплат и сальдо.
- **Новый регистр кредиторки в 1c vs reuse `supplier_debt_movement` из 1b.** Выбран reuse existing регистра 1b. Поступление сырья уже создаёт долг поставщику в `supplier_debt_movement`; payment_out должен погашать этот же поток, иначе кредиторка раздвоится.
- **Справочник денежных счетов vs один `money_balance`.** Выбран один регистр денег без справочника счетов, потому что первая очередь должна показать общий денежный результат. Касса/банк, статьи ДДС и перемещения денег явно вынесены за scope.
- **Цена отгрузки только ручным вводом vs команда из `price_list`.** Выбрана команда подготовки отгрузки: `price_list` уже создан в 1a как источник цен продукции, поэтому пользователь не должен вручную искать цену при каждой отгрузке. При этом сложные индивидуальные цены и скидки не добавляются.
- **Блокировать отгрузку сверх остатка на уровне проведения vs команда подготовки.** Выбрана команда подготовки, потому что она опирается на подтверждённые programmable commands и QueryBuilder. Неподтверждённый механизм автоматического save-hook не используется как обязательный.
- **Разносить оплаты по конкретным отгрузкам/поступлениям vs сальдо по контрагенту.** Выбрано сальдо по контрагенту. Это проще, соответствует первой очереди и не требует договоров, счетов и авансов.

## 4. Граница scope

### Что войдёт в основное ТЗ

- Документ `shipment` с подготовкой цен и остатка ГП.
- Проведение `shipment` в `finished_goods_movement` и `customer_settlements`.
- Документ `payment_in` с движением денег и погашением дебиторки.
- Документ `payment_out` с движением денег и погашением кредиторки.
- Новые регистры записей `customer_settlements` и `money_balance`.
- Reuse existing `supplier_debt_movement`, `finished_goods_movement`, `price_list` без изменения их состава.
- Отчёты `customer_debt_report`, `supplier_debt_report`, `money_flow_report`.
- Минимальная навигация в меню, если существующий `autoFill` не покрывает новые объекты.

### Что НЕ войдёт (явно)

- Закрытие месяца и средневзвешенное списание стоимости сырья.
- Себестоимость готовой продукции, валовая прибыль, P&L и баланс.
- Договоры, счета, авансы и разнесение оплат по документам.
- Касса/банк как отдельные счета, статьи ДДС и перемещения денег.
- Доставка, маршруты, экспедиторы и возвраты клиентов.
- Индивидуальные цены, скидки, бонусы клиентов.
- Формы-конструкторы, если автоформ достаточно.

## 5. Открытые архитектурные вопросы для PM

Открытых архитектурных вопросов нет. PM 2026-06-11 выбрал стандартный scope 1c: отгрузка, оплаты, расчёты, деньги, отчёты дебиторки/кредиторки/движения денег. Закрытие месяца не включается.

Технические детали реализации — состав колонок, имена `.bjs`, фильтры data_view, порядок импорта — зафиксированы в `sp-001-bakery-stage1c.json` и не являются открытыми архитектурными вопросами.
