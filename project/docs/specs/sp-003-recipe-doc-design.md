# Методика решения — документ рецепта и регистр норм

> **Назначение документа.** Зафиксировать архитектурный подход к замене неудобной модели рецептур `catalog/recipe` + `register/recipe_component` на пользовательский документ `operation/recipe_doc` с табличной частью компонентов, проведением в регистр норм и автоматической миграцией старых рецептур. Этот markdown-дизайн является primary design artifact для ТЗ `sp-003-recipe-doc.json`.

---

## 1. Бизнес-задача

Текущая модель рецептур была сделана как компромисс 1a: шапка рецептуры хранится в `catalog/recipe`, строки состава — в отдельном `register/recipe_component`. Такая модель технически работает для расчёта потребности и списания сырья, но неудобна пользователю: шапка и строки вводятся в разных местах, история изменения рецептов не видна как последовательность документов, нет даты рецепта как бизнес-события, а актуализация нескольких рецептов на одно изделие контролируется только алгоритмами.

Новая модель должна сделать рецепт привычным документом. Пользователь создаёт документ «Рецепт», указывает дату, выходную номенклатуру, количество выхода в базовой единице этой номенклатуры и строки компонентов с расходом на указанное количество выхода. При сохранении/проведении документ создаёт записи регистра норм. Расчёты потребности и выпуска больше не читают старые `catalog/recipe` и `register/recipe_component`; они выбирают последний проведённый рецепт на дату расчёта.

Решение сохраняет историю рецептов. Старые рецепты не деактивируются отдельным флагом и не удаляются: новый рецепт с более поздней датой становится актуальным на свою дату и позже, а старый остаётся применимым для расчётов прошлых дат.

## 2. Архитектурный подход

### 2.1. Новые и изменяемые объекты

| Действие | Вид | Имя | Назначение |
|---|---|---|---|
| CREATE | records | `recipe_norm` | Проведённые строки рецептов: нормализованный расход компонента на 1 единицу выхода. |
| CREATE | operation | `recipe_doc` | Документ «Рецепт» с шапкой выхода и табличной частью компонентов. |
| CREATE | workflow | `migrate_recipe_docs` | Однократная миграция старых `catalog/recipe` + `register/recipe_component` в новые документы рецептов с проведением. |
| MODIFY | workflow | `requirement_calc` | Расчёт потребности читает `records/recipe_norm` вместо старой пары объектов. |
| REUSE | operation | `production_task` | Документ задания на производство остаётся точкой запуска расчёта потребности через существующую команду `calc_requirement`. |
| MODIFY | operation | `production_output` | Команда расчёта списания сырья читает `records/recipe_norm` вместо старой пары объектов. |
| MODIFY | catalog | `recipe` | Старый объект остаётся как источник миграции/архив; после миграции не используется в расчётах. |
| MODIFY | register | `recipe_component` | Старый объект остаётся как источник миграции/архив; после миграции не используется в расчётах. |

Техническое имя нового документа — `recipe_doc`, потому что имя `recipe` уже занято `catalog/recipe` и зарегистрировано в `metadata/system/dataTypes.json`. Интерфейсное название нового документа — «Рецепт».

### 2.2. Документ `operation/recipe_doc`

Шапка документа содержит стандартные поля операции (`number`, `date`, `is_deleted`, `is_files`, `create_records`) и бизнес-поля:

| Поле | Назначение |
|---|---|
| `output_item` | Выходная номенклатура: только `product` или `semi_product`. |
| `output_qty` | Количество выхода в базовой единице `output_item`; больше 0. |
| `output_unit` | Справочная единица выхода из `catalog/nomenclature.unit`; заполняется командой проверки/миграцией. |
| `comment` | Технологическое примечание. |

Табличная часть `components` хранит расход компонентов именно на `output_qty` из шапки, а не на единицу выхода:

| Поле | Назначение |
|---|---|
| `component` | Компонент рецепта: только `raw` или `semi_product`. |
| `component_unit` | Справочная единица компонента из `catalog/nomenclature.unit`; заполняется командой проверки/миграцией. |
| `quantity` | Расход компонента на количество выхода `output_qty`; больше 0. |
| `comment` | Примечание строки. |

Запрет компонента с единицей `шт` не вводится. Все количества вводятся только в базовых единицах номенклатуры; пересчёт `г ↔ кг`, `шт ↔ упаковка` и т.п. не входит в scope.

### 2.3. Регистр `records/recipe_norm`

`records/recipe_norm` является расчётным источником для потребности и списания сырья. Документ пишет по одной записи регистра на каждую строку табличной части `components`.

Ключевые поля регистра:

| Поле | Назначение |
|---|---|
| `period` | Дата документа рецепта. |
| `output_item` | Выходная номенклатура. |
| `output_qty` | Количество выхода, указанное в документе. |
| `output_unit` | Справочная единица выхода. |
| `component` | Компонент. |
| `component_unit` | Справочная единица компонента. |
| `component_qty` | Расход компонента на `output_qty`. |
| `component_qty_per_unit` | Нормализованный расход компонента на 1 единицу выхода: `$r.quantity / $h.output_qty`. |

Стандартные колонки records (`meta_object`, `object_uid`, `row`) сохраняют связь записи с документом «Рецепт». Повторное сохранение документа не должно дублировать нормы: штатный механизм проведения удаляет старые записи текущего документа и создаёт новые.

Проведение не должно вычислять `component_qty_per_unit`, если `output_qty <= 0`. Команда проверки ловит эту ошибку на пользовательском сценарии, а recordsSettings должны дополнительно иметь условие проведения строк, которое защищает выражение деления от нулевого знаменателя даже при сохранении в обход команды.

### 2.4. Правило актуальности

Актуальный рецепт для расчёта по позиции `output_item` на дату `D` — это проведённый документ «Рецепт» с максимальным `period`, где `period <= D`. Все строки компонентов этого документа берутся из `records/recipe_norm` по паре `output_item + period + object_uid`.

Бизнес-правило PM: не может быть двух рецептов с одной датой для одной выходной номенклатуры. Так как подтверждённого механизма композитного уникального ограничения `output_item + date` для операций в текущей evidence-базе нет, методика не закладывает неподтверждённый DB-unique. Вместо этого:

- команда проверки рецепта должна искать существующий `recipe_doc`/`recipe_norm` с тем же `output_item` и той же `date`, исключая текущий документ при повторном сохранении;
- workflow миграции должен остановиться, если старые рецептуры дают дубль даты для одного выхода;
- `requirement_calc` и `calc_raw_writeoff` должны останавливать расчёт с понятной ошибкой, если в `recipe_norm` найдено больше одного `object_uid` для `output_item + period`, выбранного как актуальный.

Если позже будет подтверждён композитный unique-index на уровне metadata, его можно добавить отдельным техническим улучшением.

### 2.5. Миграция старых рецептур

Старые данные должны быть перенесены автоматически. Для этого создаётся ручной workflow `migrate_recipe_docs`:

1. Прочитать `catalog/recipe` и `register/recipe_component`.
2. Для каждой старой рецептуры создать один `operation/recipe_doc`.
3. Перенести `recipe.output_item` в `recipe_doc.output_item`, `recipe.output_qty` в `recipe_doc.output_qty`.
4. Перенести строки `recipe_component` в `recipe_doc.components`: `component`, `quantity`, `comment`.
5. Заполнить справочные `output_unit` и `component_unit` по `catalog/nomenclature.unit`.
6. Сохранить документ с `CreateRecords = true`, чтобы сразу создать записи `records/recipe_norm`.
7. Записать в `comment` маркер миграции старого recipe id/title, чтобы повторный запуск мог пропустить уже перенесённые рецепты.

Для даты мигрированного рецепта используется контролируемое значение, заданное в workflow/скрипте миграции. Дата миграции должна быть не позже самой ранней даты существующих документов, которые рассчитываются по рецептам (`operation/production_task.plan_date` и `operation/production_output.date`), чтобы пересчёт исторических документов после миграции находил рецепт по правилу `period <= дата расчёта`. Если таких документов на стенде нет, допустима дата запуска миграции; выбранное значение инженер фиксирует в implementation report/import notes.

Старые `catalog/recipe` и `register/recipe_component` после миграции не удаляются. Их можно скрыть из пользовательской навигации, но они остаются источником аудита миграции и fallback до приёмки.

### 2.6. Обновление расчётов

`workflow/requirement_calc` и `operation/production_output.command.calc_raw_writeoff.bjs` должны читать не старую пару объектов, а `records/recipe_norm`.

`requirement_calc` используется не только выпуском продукции. Существующая команда `operation.production_task.command.calc_requirement.bjs` запускает этот workflow для документа `operation/production_task`, передавая `task_number`; сам workflow читает `production_task.plan_date` и табличную часть `plan_products`. Поэтому update `requirement_calc` должен сохранить прежний контракт результата для задания на производство. Для этой ветки дата расчёта рецепта — `production_task.plan_date`.

Алгоритм раскрытия рецептов сохраняется по смыслу:

1. Для каждой выходной позиции найти актуальный документ рецепта на дату расчёта.
2. Проверить, что рецепт существует.
3. Проверить, что для выбранной даты нет нескольких документов рецепта по одному `output_item`.
4. Для каждой строки нормы рассчитать потребность компонента как `qty * component_qty_per_unit`.
5. Если компонент — `semi_product`, рекурсивно раскрыть его рецепт.
6. Если компонент — `raw`, добавить сырьё в итог.
7. Если компонент — `product`, остановиться с ошибкой.
8. Сохранять текущие проверки циклов, положительных количеств и достаточности остатка сырья для выпуска.

### 2.7. Формы и пользовательский сценарий

Так как задача началась из UX-проблемы, формы списка и редактирования для `recipe_doc` входят в scope сразу.

Форма списка должна показывать дату, номер, выходную номенклатуру, количество выхода, единицу выхода и комментарий.

Форма редактирования должна показывать шапку рецепта и табличную часть компонентов в одном экране. В форме должна быть доступна команда «Проверить рецепт», которая:

- проверяет заполненность `output_item`, `output_qty`, компонентов и количеств;
- проверяет типы номенклатуры: выход только `product`/`semi_product`, компонент только `raw`/`semi_product`;
- заполняет справочные единицы `output_unit` и `component_unit`;
- проверяет запрет дубля `output_item + date`;
- проверяет отсутствие компонента, совпадающего с выходом;
- возвращает понятные ошибки пользователю.

Жёсткая автоподстановка единиц прямо при выборе номенклатуры не закладывается как обязательная capability, потому что она не подтверждена текущими evidence-источниками. Заполнение единиц командой и миграцией опирается на подтверждённые programmable commands и QueryBuilder.

## 4. Рассмотренные альтернативы

- **Доработать старый `catalog/recipe` формами.** Отвергнуто: у `catalog` нет табличных частей (`kind.catalog.json`, `useDetailsTables = false`), а хранение строк в отдельном register остаётся неудобным и не даёт документной истории.
- **Оставить `is_active` в новом документе.** Отвергнуто PM: актуальность определяется датой последнего проведённого рецепта. Старые рецепты остаются историей и проигрывают по дате.
- **Хранить в строках документа норму на 1 единицу выхода.** Отвергнуто PM: пользователь вводит расход на то количество выхода, которое указано в шапке. Нормализация выполняется при проведении в `records/recipe_norm`.
- **Удалить старые объекты после миграции.** Отвергнуто для первого шага: старые объекты нужны как источник автоматической миграции и для контроля результата. Удаление можно рассмотреть после стендовой приёмки.
- **Ввести пересчёт единиц.** Отложено: нет модели коэффициентов пересчёта единиц и PM снял это требование. Все количества вводятся в базовых единицах номенклатуры.

## 5. Граница scope

### Входит

- Новый документ `operation/recipe_doc` с табличной частью `components`.
- Новый регистр `records/recipe_norm`.
- Формы списка и редактирования для `recipe_doc`.
- Команда проверки рецепта и заполнения справочных единиц.
- Проведение `recipe_doc` в `recipe_norm` с нормализацией `component_qty_per_unit = quantity / output_qty`.
- Workflow миграции старых `catalog/recipe` + `register/recipe_component` в новые документы.
- Обновление `requirement_calc` на чтение `recipe_norm` с сохранением контракта для `production_task.calc_requirement`.
- Обновление `production_output.calc_raw_writeoff` на чтение `recipe_norm`.
- Сохранение старых объектов как архив/fallback без участия в новых расчётах.

### Не входит

- Пересчёт между разными единицами измерения.
- Жёсткий неподтверждённый DB-unique по `output_item + date`.
- Автоподстановка единиц непосредственно в момент выбора номенклатуры без команды.
- Удаление старых `catalog/recipe` и `register/recipe_component`.
- Себестоимость, закрытие месяца, технологические карты, потери/выходы, версии с утверждением и маршруты производства.

## 6. Открытые вопросы

Открытых бизнес-вопросов нет. PM 2026-06-12 подтвердил: стенд синхронизирован; выход только `product`/`semi_product`; компоненты только `raw`/`semi_product`; количества только в базовой единице; пересчёта единиц нет; актуальность по последнему проведённому рецепту на дату; два рецепта на один выход с одной датой запрещены; старые рецепты мигрируются автоматически; дата миграции должна сохранять пересчёт исторических `production_task`/`production_output`; формы обязательны.

Технический риск остаётся по механизму жёсткого уникального ограничения `output_item + date`: пока capability не подтверждена, защита проектируется через команду проверки, миграцию и guards в расчётах.
