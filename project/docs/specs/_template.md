## Как читать этот документ

Документ описывает изменения, которые Инженер должен внести в метаданные проекта (`metadata/`).

Структура:

- **Разделы 1–2** — *зачем* и *в каких границах* делается изменение. Это контекст, который полезен и человеку, и Инженеру.
- **Раздел 3** — короткая сводная таблица: что вообще меняется.
- **Раздел 4** — детали по каждому метаобъекту: какие колонки, какие связи, какое проведение, какие расчёты, какие команды и workflow.
- **Раздел 5** — изменения в меню (если есть).
- **Раздел 6** — порядок реализации, если объекты зависят друг от друга.
- **Раздел 7** — чек-лист приёмки. Без галочек по этому чек-листу ТЗ не считается реализованным.
- **Разделы 8–9** — открытые вопросы и история статусов.

В таблицах полей обязательность маркируется словом в колонке `Обязательно`:

- **«да»** — поле обязательно заполнить.
- **«нет, дефолт: X»** — поле опционально; если пусто, используется указанный дефолт.
- **«по ситуации»** — заполняется только в применимых случаях. Например, `Condition` в правиле проведения по регистрам — только когда нужна фильтрация; `RecordsSources` — только когда записи нельзя получить из шапки или одной табличной части напрямую.

Имена `Name` объектов, колонок, табличных частей, источников записей и т. п. — **всегда латиница, snake_case, ≤30 символов** (ADR-001).

## 7. Чек-лист приёмки

Чек-лист разделён по тому, **кто** и **как именно** проверяет пункт. Аналитик при заполнении раскладывает пункты по трём корзинам — A, B, C — в зависимости от способа проверки. Без явного разделения было не понятно, где заканчивается ответственность Инженера и начинается ответственность PM.

### A. Файловая самопроверка (Инженер)

Проверяется чтением собственных JSON-файлов и валидацией по JSON-схемам, **без запуска BaSYS**. Сюда попадают универсальные пункты, применимые к большинству ТЗ.

- [ ] Все метаобъекты из раздела 3 созданы / изменены / удалены согласно действию.
- [ ] Все JSON валидируются по соответствующим JSON-схемам.
- [ ] Имена `Name` — латиница `snake_case`, ≤30 символов (ADR-001).
- [ ] `MetaObjectKindUid` и `DataTypeUid` — взяты из `metadata/system/`, не из `reference/` (ADR-002).
- [ ] `Memo` заполнено у каждого нового объекта и каждой новой колонки.
- [ ] Свежие UUID v4 у каждого нового `Uid` (объект, колонки, табличные части, команды, источники).
- [ ] У объектов с видом `IsReference = true` (catalog, enum, operation и т. п.) — запись добавлена в `metadata/system/dataTypes.json`.
- [ ] Имена `.bjs`-файлов точно совпадают со значениями `Expression` в JSON.
- [ ] Все команды, workflow и расчётные правила из ТЗ представлены в metadata или явно отмечены как не требующие отдельного metadata-объекта.

### B. Декларативные проверки по JSON (Инженер)

Поведение системы можно подтвердить, проверив конкретное поле в собственном JSON. Например: «поле `X` скрыто из формы» подтверждается тем, что у переопределения `RenderSettings.ShowInItem: false` стоит. Это **не запуск системы**, а сверка «утверждение об ожидаемом поведении ↔ соответствующее поле в JSON».

- [ ] *(пример)* Колонка `X` дефолтно `false` — у `DataSettings.DefaultValue` стоит `"false"`.
- [ ] *(пример)* Поле `Y` не отображается в списке — у `RenderSettings.ShowInList: false` стоит.
- [ ] *(пример)* Команда `Z` привязана к шапке — `Commands[].TableUid` равен `Header.Uid`.
- [ ] *(пример)* Команда `fill_table` вызывает утверждённый workflow / обработчик.
- [ ] *(пример)* Расчётное поле `total_amount` имеет утверждённую формулу или workflow-шаг пересчёта.

### C. Функциональные проверки на стенде (PM)

Поведение проверяется **только после импорта на сервер BaSYS** — открытие формы, ввод данных, нажатие кнопок, проверка сортировки/фильтрации, межсессионные сценарии. Инженер на этом этапе уже не участвует — это работа PM на стенде.

- [ ] *(пример)* При создании документа `sale` с заполненной табличной частью `goods` — в регистре `records.stock` появляются записи на `–<quantity>` по каждой строке.
- [ ] *(пример)* Существующую карточку можно открыть, отредактировать любое поле и сохранить.
- [ ] *(пример)* Скидка `discount_percent` корректно применяется в итоговой сумме документа.
- [ ] *(пример)* Команда `fill_table` заполняет строки из контрольного файла без дублей при повторном запуске.
- [ ] *(пример)* Workflow возвращает понятную ошибку, если входной файл отсутствует или имеет неверный формат.

> **Подсказка Аналитику** при раскладке пунктов по корзинам:
> - Если пункт можно проверить, открыв JSON-файл и посмотрев на конкретное поле — это **A** или **B**. A — универсальные правила формирования файла; B — конкретное поведение, обеспечиваемое конкретным полем.
> - Если пункт требует «работает», «открывается», «срабатывает», «принимает ввод», «отображает» — это **C**.
> - Пункты в корзине C — не повод размышлять «а смог бы Инженер это проверить как-то ещё»; если требуется запущенная BaSYS, это автоматически зона PM.
