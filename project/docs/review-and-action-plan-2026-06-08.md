# Ревью create-model-3 и план действий к автономному агенту (ред. 2)

> Дата: 2026-06-08. Документ подготовлен в Claude Code по итогам ревью проекта и обсуждения. Параллельно дорабатывается в Ultraplan — эта копия отражает локальную версию на момент сохранения.

## Контекст

`create-model-3` — «фабрика» ИИ-агентов для создания коробочного решения хлебозавода на low-code платформе **BaSYS**. Разрабатывалась в **OpenCode**, открыта в **Claude Code**. Цель владельца — «независимый агент, который сам всё делает». Этот документ — ревью + план действий, переработанный по итогам обсуждения.

Зафиксированные в беседе вводные:
- **Миграцию на Claude Code пока не делаем** отдельной задачей — адоптируем её фичи точечно, когда они нужны под конкретный приём.
- **Целевая автономия — «гейты только на бизнесе»:** агент сам гоняет весь внутренний цикл; человек утверждает бизнес-смысл и финальную приёмку.
- **У BaSYS нет import-API/CLI** — но это **больше не потолок**: появился браузерный путь (см. ниже).

---

## Сквозной принцип (спина всего плана)

> Чем больше работы делает **детерминированный код**, тем меньше поверхность, на которой LLM может ошибиться — а ошибаться особенно опасно там, где результат нельзя проверить на стенде. Поэтому: максимум механики отдаём коду, за LLM оставляем только суждение, а проверку **сдвигаем влево** — вплоть до самостоятельного прогона в браузере.

**Разделение труда:**

| Слой работы | Кому | Почему |
|---|---|---|
| Печать JSON-скелетов metadata (колонки, стандартные поля, `$schema`, UID, camelCase, RecordsSettings) | **код — генератор** | чистый шаблон, ума не требует; correct-by-construction |
| Механические проверки (валидность JSON, имена, UID, ссылки, порядок импорта) | **код — валидатор** | один формально точный ответ |
| *Какие* объекты/колонки/типы нужны, бизнес-смысл, архитектура | **LLM** | суждение, шаблоном не покрыть |
| `.bjs`-логика (разузлование и пр.) | **LLM** | настоящая логика |
| Импорт и проверка результата на стенде | **браузер-агент** (+ человек на бизнес-приёмке) | физический доступ только через UI |

Формула цели: **LLM проектирует → генератор печатает → валидатор страхует → браузер-агент импортирует и сверяет → человек подтверждает бизнес-смысл.**

## Ревью

### Сильные стороны
1. **Зрелый процесс** design→spec→plan→impl→audit с возвратом «владельцу ошибки» (`project/docs/workflow.md`).
2. **Evidence Rule** (`AGENTS.md:12-33`) против галлюцинаций — уже окупился (ADR 2026-06-02).
3. **Независимый аудит** — `metadata-auditor` намеренно не читает отчёт инженера.
4. **Трёхуровневая модель сложности** (quick / single-agent / multi-agent) по риску.
5. **Управление знанием** — ADR, glossary, `patterns/`; знание извлекается из прогонов.
6. **Двухслойная защита read-only зон** — permissions + плагин `readonly-guard.ts`.
7. **PM не читает JSON построчно** (`AGENTS.md:45`) — верное распределение труда.

### Слабые стороны (и куда их закрывает план)
1. **Инфраструктура завязана на OpenCode** — в Claude Code не работает as-is. → Фаза 3 (точечная адопция, не big-bang).
2. **Корректность держится на дисциплине, а не на механике** — нет ни одного автоматического валидатора. → Фаза 1 (валидатор).
3. **Генерация JSON — механическая работа, выполняемая LLM.** Сотни строк шаблонного JSON пишет модель → большая поверхность для ошибки там, где её нельзя проверить на стенде. → Фаза 1 (генератор).
4. **Разрыв автономии — ручной импорт/приёмка.** → Фаза 2 (браузер) частично замыкает цикл уже сейчас.
5. **Память: живой слой держится компакцией.** Слой состояния (`PROJECT_CONTEXT.md`, `OPEN_QUESTIONS.md`) хорош; но внутрисессионный контекст между снимками держится ручным тюнингом `tail_turns:3` — отсюда хрупкость. → Фаза 3 (auto-memory + `rules/*.md`).
6. **Человек — узкое место на 4 гейтах за цикл.** → Фаза 3 (оркестратор с 2 бизнес-гейтами).
7. **Гигиена и дублирование правил** — `.opencode/node_modules/` в дереве; naming-правила размазаны по многим файлам. → Фаза 0.

## План действий (по фазам)

Фазы 1 и 2 дают максимум пользы и **не требуют миграции** — это самостоятельный код/тулинг, ценный в любом харнессе.

### Фаза 0 — Гигиена и единый источник правды (дёшево, сразу)
- Добавить `.opencode/node_modules/` в `.gitignore`.
- Свести naming-политику (snake_case ≤30, список SQL-reserved, стандартные колонки) и read-only зоны в **один машиночитаемый файл правил** — на него обопрутся и валидатор, и генератор. Источники сейчас: `decisions.md`, `patterns/metadata-workflow.md`, `metadata-auditor.md`.

### Фаза 1 — Детерминированное ядро (платформонезависимо, наибольший ROI)
**1a. Валидатор** (быстрый, маленький — делаем первым как страховку и де-риск):
- проверки: валидный JSON + `$schema`; `Name` латиница snake_case ≤30, не reserved, не коллизия со стандартными колонками; UID из своего `metadata/system/`; резолв всех cross-references, отсутствие дублей; выполнимость алфавитного порядка импорта.
- сначала прогнать на **уже принятой metadata этапа 1a** → обязан пройти «зелёным» (нет ложных срабатываний), затем поймать заведомую ошибку.

**1b. Генератор** (бóльшая инвестиция, наибольшее сжатие ошибки):
- ввести компактный **исходник-намерение** (YAML/мини-JSON: вид, имя, колонки, типы);
- генератор разворачивает его в полный BaSYS-JSON: стандартные колонки, UID, схема, camelCase, RecordsSettings.
- **бонусы:** correct-by-construction (валидатор почти не нужен); Evidence Rule встроен (нет шаблона — нельзя сгенерировать несуществующую возможность, те две галлюцинации из ADR стали бы невозможны); PM ревьюит 10 строк исходника, а не 500 строк JSON.
- основа уже есть — скиллы `create-catalog/enum/register/operation/fill-workflow`: превратить их из инструкций-для-LLM в **код**.
- граница: `.bjs`-логику по-прежнему пишет LLM.

### Фаза 2 — Замыкание цикла через браузер (большой скачок автономии; не требует API BaSYS)
Подтверждено документацией: Claude Code водит реальный браузер через **Playwright MCP** (офиц. плагин Anthropic; `@playwright/cli` в ~4× экономнее по токенам) — `navigate/click/type/snapshot(DOM)/screenshot/evaluate`, работа с авторизованной сессией.

**2a. Read-only спайк (первый и безопасный):** на **отдельном тестовом стенде** под **тестовым аккаунтом** агент логинится → открывает готовый отчёт 1a → читает значение → сверяет. Цель — закрыть **главный неизвестный: отдаёт ли BaSYS читаемый DOM** (текст в таблицах) или рендерит в `canvas`. Это решается экспериментом, не теорией.

**2b. Если DOM читается:** агент исполняет **smoke-сценарий приёмки** как скрипт — импорт в порядке из `import-notes`, создание документов, запуск `requirement_calc`, чтение отчёта, сверка с ожидаемым; цикл **импорт→проверка→починка** крутится автономно, человек подключается только на бизнес-приёмке.

**Защита (обязательно):** только тестовый стенд (не прод), тестовый аккаунт, деструктив под гейтом; боевой вход агенту не давать.

> Это поднимает браузерный путь **выше** прежнего пункта «MCP, когда появится import-API»: он доступен сейчас и ничего не требует от BaSYS.

### Фаза 3 — Харнесс и автономия (адопция Claude Code)
- **Один автономный оркестратор** (перенос логики `autopilot-orchestrator`): гоняет весь цикл на субагентах, останавливается через **AskUserQuestion** только на (а) бизнес-утверждении дизайна и (б) приёмке.
- **Память:** `CLAUDE.md` с `@`-импортом существующего `AGENTS.md` (без дублирования) + `.claude/rules/*.md` с `paths`-frontmatter (naming-правила — только при работе в `metadata/`) + **auto-memory**. Снимает агрессивную компакцию.
- **Хуки:** валидатор из Фазы 1 как **PostToolUse** (после правок `metadata/`) и **Stop** (финальный гейт — агент не может закончить с красным валидатором); `readonly-guard` как **PreToolUse**/deny-правила (покрывает и `bash rm`).

### Фаза 4 — Упаковка и будущее
- **Plugin** (после стабилизации `.claude/`): упаковать агентов/скиллы/хуки/команды/генератор/валидатор в версионируемый пакет — нативная замена `bootstrap-basys-project`, один источник правды на все проекты.
- **MCP-через-API** — только если BaSYS когда-нибудь отдаст import-API; теперь это запасной путь, т.к. браузер закрывает большую часть. При случае спросить команду BaSYS.

## Рекомендуемый первый шаг

Стартовать **двумя параллельными ветками** — максимум информации за минимум затрат:
1. **Валидатор (Фаза 1a)** — быстрый, безопасный, платформонезависимый; де-рискует всё остальное и сразу даёт страховку.
2. **Read-only браузерный спайк (Фаза 2a)** — отвечает на единственный главный неизвестный (читается ли DOM BaSYS), от которого зависит весь потолок автономии.

Генератор (1b) — следующий по величине рычаг, начинать после того, как валидатор зафиксирует правила.

## Открытые / спорные вопросы
1. **Язык ядра** (валидатор/генератор): Node (ближе к `.bjs`/JSON) или Python (workspace под Python-env).
2. **Формат компактного исходника** генератора (YAML vs мини-JSON) и его охват (какие виды покрываем первыми).
3. **Тестовый стенд для браузера:** есть ли отдельный/сбрасываемый стенд и тестовый аккаунт; читаемость DOM BaSYS.
4. **Когда и как мигрировать** на Claude Code (точечно по фазам vs разом) — решаем после Фаз 1–2.
5. Полнота списка SQL-reserved и edge-cases naming — финализировать в файле правил Фазы 0.

## Как проверять (по фазам)
- **Фаза 1a (валидатор):** зелёный на принятой metadata 1a; ловит подсунутую ошибку (reserved-имя, битый UID) и блокирует Stop.
- **Фаза 1b (генератор):** из компактного исходника 1a генерится JSON, побайтово/структурно эквивалентный текущему принятому; валидатор на выходе зелёный.
- **Фаза 2a (спайк):** агент читает конкретное значение из отчёта 1a в браузере и оно совпадает с фактом на стенде.
- **Фаза 2b:** агент проходит весь smoke-сценарий и корректно отделяет «сошлось» от «дефект».
- **Фаза 3:** на малой задаче (1–2 объекта) человека спрашивают ровно дважды; после `/compact`/нового сеанса агент помнит правила без напоминания.
- **Фаза 4:** `/plugin install` поднимает фабрику в чистом workspace без ручного копирования.
