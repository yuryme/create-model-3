# Журнал архитектурных решений (ADR)

Этот файл — журнал принципиальных решений по проекту в стиле Architecture Decision Records.
Сюда попадают **значимые** архитектурные выборы, которые потом помогут понять, почему модель построена именно так.

## Что писать сюда

- Выбор структуры регистров (один общий vs несколько отдельных).
- Решение про источник данных для проведения (header / табличная часть / RecordsSource).
- Выбор между Панелью данных и Отчётом Excel под конкретную задачу.
- Принципиальные ограничения области автоматизации.
- Любой выбор, который позже захочется обосновать перед собой или командой.

## Что НЕ писать сюда

- Мелкие правки имён колонок и формул — это обычные коммиты, не ADR.
- Рабочие правила проекта — для них есть `AGENTS.md` и `.opencode/skills/` в корне workspace.
- Текущие открытые вопросы — для них `OPEN_QUESTIONS.md` в корне workspace.

## Шаблон записи

```markdown
## YYYY-MM-DD: <Короткий заголовок решения>

**Обоснование.** Почему именно так.

**Последствия.** Что меняется в системе или в работе из-за этого выбора.
```

## 2026-05-15: Свой `system/` — первоисточник UID для целевой инсталляции, а не `reference/`

**Контекст.** В первой версии правил мы считали `reference/metadata/system/` (выгрузка чужой работающей системы) источником UID видов и типов. Когда пользователь добавил в проект **пустую модель** через `metadata/`, выяснилось, что каждая выгрузка BaSYS приходит со своим `system/`, содержащим `dataTypes.json`, `kinds/` и `schemas/`. UID одних и тех же видов/типов в разных инсталляциях **отличаются** — UID — это идентификаторы строк в БД конкретной инсталляции, а не глобально универсальные имена.

**Решение.** Первоисточник UID видов, типов и JSON-схем для нашей целевой системы — **`metadata/system/`** (свой). `reference/metadata/system/` для UID **больше не использовать** — он подходит только как ориентир «такие типы существуют».

**Обоснование.** UID-ы, скопированные из чужой инсталляции, приведут к битым ссылкам при импорте в нашу целевую BaSYS: сервер будет искать тип/вид по UID, не найдёт, объекты не примет. Единственный корректный путь — брать UID из `system/` нашей целевой инсталляции.

**Последствия.**
- В скилле `basys-metadata` все ссылки на `../../../reference/metadata/system/` заменены на `../../../metadata/system/` (12 правок в 6 файлах).
- Шаг 11 из «Adding a New Metaobject» (запись в `dataTypes.json` при создании reference-kind объектов) — **теперь применим**: у нас есть локальный `dataTypes.json`, в который можно дописывать.
- Маленькая правка: `dataTypes.json` — единственный файл в `system/`, который мы дописываем; остальное (kinds/, schemas/) — read-only.
- В скилле специально оговорено, что **UID-ы из чужого `reference/` не использовать**, в т.ч. UID-ы из таблиц в `data-view-reports.md` и `workflows.md` (которые пришли из Cursor-rules) — обязательно сверять со своим `system/`.
- `reference/metadata/system/` теперь полностью **read-only банк примеров**: можно подсматривать структуру и схемы, нельзя брать оттуда UID.

## 2026-05-15: Имена объектов и колонок (`Name`) — только латиница snake_case

**Контекст.** В референсной выгрузке (`reference/metadata/`, БД `elevator`) часть `Name` объектов и колонок написана **кириллицей** (`акт_монтаж_ме`, `карточка_договора`, `согласование_договоров` и т.д.). BaSYS это технически допускает — в существующей системе работает. Изначальное жёсткое правило «только латиница» из удалённого `basys-knowledge-base.md` оказалось не общеплатформенным. Рассматривались два варианта: (а) принять кириллицу как допустимую и для новых объектов тоже; (б) для новых писать только латиницей, миря́сь с тем, что в `reference/` встречаются оба стиля.

**Решение.** Вариант (б): **все новые `Name` — только латиница snake_case** (`[a-z0-9_]`, длина ≤30 символов). Правило применимо к именам объектов метаданных, таблиц и колонок в `metadata/`.

**Обоснование.** Кириллические идентификаторы:
- Имена SQL-таблиц/полей с не-ASCII символами тянут проблемы кодировок при бэкапе/восстановлении, репликации, межсистемной интеграции.
- В URL автоформ — нужно URL-encoding, увеличивается риск багов на пограничных кейсах.
- Скрипты выражений `$h.<имя>`, `$r.<имя>` — лучше работают с ASCII-идентификаторами (меньше неожиданностей при копировании, при ручной правке в редакторах).
- Существующие объекты на кириллице работают по инерции; ставить новые на ту же траекторию — закладывать долговую мину.

**Последствия.**
- Новые объекты в `metadata/` — `Name` только латиницей snake_case ≤30 символов.
- `Title` и `Memo` — можно по-русски (это отображаемые/комментарийные поля, в логике системы не участвуют).
- При копировании паттерна из `reference/` объекта с кириллическим `Name` — переименовать в латиницу при адаптации.
- Это правило входит в чек-лист `.opencode/skills/basys-metadata/SKILL.md`.
- Существующие объекты в `reference/` не трогаем — это read-only корпус.

## 2026-05-16: Порядок импорта BaSYS алфавитный; перекрёстные ссылки между видами требуют явной последовательности

**Контекст.** При импорте метаданных с перекрёстными ссылками между видами обнаружено, что сервер BaSYS не строит граф зависимостей, а обходит файлы строго **алфавитно** — сначала по папкам видов (`catalog/` → `enum/` → `menu/` → `operation/` → …), внутри каждой папки — по объектам. Тип данных регистрируется только в момент импорта самого объекта; `system/dataTypes.json` — снимок, сервер на него при импорте не опирается. Если объект из более ранней папки ссылается на объект из более поздней папки, импорт всей папки одним заходом может упасть с ошибкой отсутствующего UID. Рассматривались варианты: (а) хранить только независимые партии метаданных, (б) считать такие связи ошибкой ТЗ и переписывать модель через прокси-объекты, (в) принять алфавитный порядок как платформенное ограничение и компенсировать ручной последовательностью импорта.

**Решение.** Вариант (в). Принимаем алфавитный порядок импорта как неотъемлемое свойство BaSYS. Компенсируем дисциплиной: **Инженер обязан класть в отчёт PM короткую инструкцию по последовательности импорта** в составе любой реализации ТЗ, даже когда случай тривиальный. Для случаев с перекрёстными ссылками между видами — отдельный companion-файл `<sp-id>-import-notes.md` рядом с ТЗ, с подробной последовательностью.

**Обоснование.**
- Менять платформу нельзя — мы её потребители.
- Запрещать перекрёстные ссылки между видами в ТЗ слишком ограничительно: они объективно нужны (`catalog`-объект ссылается на `enum`-классификатор — нормальная конструкция).
- Прокси-объекты или искусственные обёртки усложняют модель ради обхода ограничения импортёра.
- Знание про алфавитный порядок проверено на стенде `yuri_test` 2026-05-16; рабочий приём «удалить ссылающийся объект на сервере + повторный импорт всей папки» подтверждён, альтернатива «двойной прогон импорта» описана как менее аккуратная.

**Последствия.**
- В `.opencode/agents/engineer.md`, раздел «Specification Discipline», добавлено правило про обязательную инструкцию импорта в отчёте PM, со списком вариантов (простой случай / перекрёстная ссылка / MODIFY с новыми ссылками).
- Для нетривиальных случаев Инженер создаёт companion-файл `<sp-id>-import-notes.md` рядом с самим ТЗ.
- При проектировании ТЗ с перекрёстными ссылками Аналитик не обязан учитывать алфавитный порядок — это зона Инженера на этапе реализации.
- Если в будущей версии BaSYS появится топологический импорт — этот ADR можно будет упразднить.

## 2026-06-02: Правило доказательности — проектировать и реализовывать только на подтверждённых возможностях BaSYS

**Контекст.** Подряд два дорогих круга ревью вызваны тем, что агент принимал невподтверждённую возможность платформы за факт и строил под неё решение:
- в ТЗ 1a `catalog/recipe` был задан с табличной частью, хотя у вида `catalog` `useDetailsTables = false` (ADR-2026-06-02 о рецептурах);
- в методике sp-002 (сеялка) аналитик предположил, что workflow может запускать другой workflow на сервере, и сделал это ядром рекомендуемой архитектуры (оркестратор + вызов `requirement_calc`). Проверка показала: `runWorkflow(...)` в документации описан только для клиентского кода, среди видов шагов workflow нет «запуска процесса», а в `reference/metadata/workflow/` (115 процессов) такого паттерна нет.

В обоих случаях фантазийное допущение ловилось только на ревью, что дорого.

**Решение.** Вводится правило доказательности: `analyst` и `engineer` опираются только на подтверждённые возможности платформы. Возможность считается подтверждённой, только если (1) явно описана в `basys-docs/ru/` или (2) есть рабочий пример в `reference/metadata/`. Неподтверждённую возможность нельзя класть в основу методики, ТЗ, плана или реализации; её фиксируют как открытый риск/вопрос и проверяют на стенде/эскалируют PM до того, как от неё начнут зависеть другие решения. Для любой нетривиальной возможности автор обязан привести ссылку-доказательство; PM-chat при ревью возвращает артефакт, если возможность принята на веру.

**Обоснование.** Дешевле требовать доказательство до проектирования, чем ловить фантазии на ревью или на стенде. Правило формализует то, что и так подразумевалось AGENTS.md Evidence Rule, и делает проверку доказательств обязательной точкой ревью.

**Последствия.**
- В `AGENTS.md` добавлен раздел «Evidence Rule (Facts Only)» — первоисточник правила, читается каждую сессию.
- В `.opencode/agents/analyst.md` (Principles) и `.opencode/agents/engineer.md` (Key Rules) добавлены соответствующие требования.
- В шаблоны `_design-template.md` и `_plan-template.md` добавлено требование сопровождать каждую нетривиальную возможность ссылкой-доказательством.
- PM-chat при ревью проверяет наличие доказательств у заявленных возможностей.
- `reference/` подтверждает только факт существования возможности; UID/значения из чужого `reference/` по-прежнему не копируются (ADR 2026-05-15).

## 2026-06-02: Рецептуры хранятся как шапка справочника + строки отдельного регистра

**Контекст.** В ТЗ хлебозавода 1a рецептура сначала была задана как `catalog/recipe` с табличной частью компонентов. Проверка показала, что в текущем `metadata/system/kinds/kind.catalog.json` у вида `catalog` стоит `useDetailsTables = false`; в `reference/metadata/catalog/` не найдено справочников с непустыми `DetailTables`. Оставлять это как риск для Инженера нельзя, потому что невозможность табличной части меняет архитектуру рецептур.

**Решение.** Рецептура моделируется двумя объектами: `catalog/recipe` хранит шапку рецептуры (выходная номенклатура, количество выхода, активность, комментарий), а `register/recipe_component` хранит строки состава со ссылкой на рецепт, компонент и количество компонента на заданный выход.

**Обоснование.** Рецептура остаётся нормативно-справочной сущностью, но строки состава вынесены в вид, который хранит самостоятельные записи без табличных частей. Это соответствует текущим ограничениям вида `catalog` и не требует от Инженера экспериментировать со справочником, который платформа помечает как не поддерживающий `detailTables`.

**Последствия.** В ТЗ и методике нельзя проектировать новые справочники с табличными частями, если у целевого вида `useDetailsTables = false`, без предварительного подтверждения документацией или рабочим референсом. Для хлебозавода `requirement_calc` читает шапки из `catalog/recipe`, а состав из `register/recipe_component`; уникальность активной рецептуры на выход контролируется алгоритмом расчёта, а не уникальным индексом `output_item`.

## 2026-06-10: Количественный склад сырья отделён от стоимостного движения сырья

**Контекст.** В проектировании этапа 1b сначала предполагалось, что регистр сырья одновременно хранит количество и стоимость сырья, а `operation/production_output` при выпуске сразу рассчитывает списание сырья по средневзвешенной стоимости. Это конфликтует с выбранной границей этапа: на первом шаге нужен оперативный количественный учёт, а расчёты стоимости и себестоимости должны выполняться позже документом закрытия месяца. Дополнительно PM указал, что регистры, хранящие движения, должны называться движениями, а остатки/сальдо должны быть результатом отчётов.

**Решение.** Разделить контуры и привести регистры 1b к движенческому именованию: `records/raw_movement` ведёт только количественные движения сырья, `records/raw_cost_movement` ведёт движения стоимости сырья, `records/finished_goods_movement` ведёт движения готовой продукции, `records/supplier_debt_movement` ведёт движения долга поставщикам. В 1b поступление сырья пишет количество в `raw_movement`, стоимость поступления в `raw_cost_movement` и долг поставщику в `supplier_debt_movement`. Выпуск продукции в 1b списывает сырьё только количественно. Списание стоимости сырья по средней стоимости переносится в будущий документ закрытия месяца.

**Обоснование.** Разделение позволяет выпускать продукцию и вести склад без преждевременного расчёта средней стоимости. Стоимость поступления известна и может быть отражена сразу, но расход стоимости зависит от методики закрытия периода и не должен блокировать оперативное проведение выпуска.

**Последствия.** ТЗ 1b не должно содержать `avg_price`, `amount` и `stock_amount_before` в табличной части списания сырья выпуска. Отчёты «Остатки сырья», «Остатки готовой продукции» и будущий отчёт кредиторки рассчитывают остатки/сальдо по регистрам движений. Инвентаризация 1b корректирует только количество. Стоимостные отчёты, переоценки и расход стоимости сырья проектируются вместе с закрытием месяца в следующем этапе/очереди.

## 2026-06-10: ТЗ пишется в формате spec-json-v0.1 (structured JSON), markdown-ТЗ упразднён

**Контекст.** ТЗ велись как markdown по `_template.md`. Markdown-ТЗ трудно валидировать и машинно проверять: agents (analyst/reviewer/engineer/auditor) парсят свободный текст, ошибки структуры ловятся только глазами на ревью. PM решил перевести ТЗ в структурированный JSON-формат с формальной схемой и обязательной валидацией, по аналогии с уже существующим `*.design.json`. Рассматривались варианты: (а) оставить markdown; (б) JSON только в autopilot; (в) JSON везде (ручной и autopilot) с полной JSON-schema. Выбран (в).

**Решение.** Введён формат `spec-json-v0.1`. ТЗ — это JSON-файл `project/docs/specs/<sp-id>.json` по схеме `project/docs/specs/_spec-json.schema.json` (JSON Schema draft 2020-12), образец — `_spec-template.json`. Архитектурное обоснование остаётся в `*-design.md` / `*.design.json`; ТЗ — строимый контракт для Инженера (метаобъекты, колонки, табличные части, проведение, команды, отчёты, dataTypesNotes, чек-лист A/B/C, открытые вопросы, changelog). Статус ТЗ — в `meta.status`. Валидация против схемы обязательна и автоматизирована скриптом `project/docs/specs/validate_spec.py` (Python + `jsonschema`). Markdown-шаблон `_template.md` помечен deprecated; новые ТЗ в markdown не создаются. Методики, планы, ревью, отчёты, import-notes и audit остаются в markdown.

**Обоснование.** Структурированный ТЗ даёт машинную проверку полноты и согласованности (required-поля, enum направлений/действий, snake_case имён через схему), стабильный контракт для всех agent-ролей и однозначные ссылки между объектами. Полная JSON-schema + валидатор делают проверку формальной точкой ревью, а не ручным чтением.

**Последствия.**
- Созданы `project/docs/specs/_spec-json.schema.json`, `_spec-template.json`, `validate_spec.py`.
- Первый носитель формата — `sp-001-bakery-stage1b.json` (конвертирован из `sp-001-bakery-stage1b.md`, содержание эквивалентно).
- Обновлены агенты: `autopilot-analyst` (spec/revision пишут JSON), `autopilot-reviewer` (spec-review по JSON + проверка схемы), `autopilot-engineer` и `metadata-auditor` (читают JSON-ТЗ), ручные `analyst`/`engineer`; `autopilot-orchestrator` получил узкое bash-разрешение на запуск `validate_spec.py` и шаг валидации в Phase 2.
- Обновлены `workflow.md`, `autopilot-workflow.md`, команды `spec-to-metadata-multi`, `metadata-autopilot`.
- После изменения `.opencode/agents/*` требуется перезапуск OpenCode, чтобы новые промпты/permission вступили в силу.
- Старые markdown-ТЗ (например, `sp-001-bakery-stage1a.md`, `sp-002-...`) остаются как есть; миграция в spec-json — по мере необходимости, не обязательна задним числом.
