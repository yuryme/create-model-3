# Журнал архитектурных решений (ADR)

Этот файл — журнал принципиальных решений по проекту в стиле Architecture Decision Records.
Сюда попадают **значимые** архитектурные выборы, которые потом помогут понять, почему модель построена именно так.

## Что писать сюда

- Выбор структуры регистров (один общий vs несколько отдельных).
- Решение про источник данных для проведения (header / табличная часть / RecordsSource).
- Выбор между Панелью данных и Отчётом Excel под конкретную задачу.
- Принципиальные ограничения области автоматизации.
- Любой выбор, который позже захочется обосновать перед собой или командой.

## Что НЕ писать сюда

- Мелкие правки имён колонок и формул — это обычные коммиты, не ADR.
- Рабочие правила проекта — для них есть `AGENTS.md` и `.opencode/skills/` в корне workspace.
- Текущие открытые вопросы — для них `OPEN_QUESTIONS.md` в корне workspace.

## Шаблон записи

```markdown
## YYYY-MM-DD: <Короткий заголовок решения>

**Контекст.** Какая ситуация привела к решению. Какие варианты рассматривались.

**Решение.** Что выбрано.

**Обоснование.** Почему именно так.

**Последствия.** Что меняется в системе или в работе из-за этого выбора.
```

## 2026-05-15: Свой `system/` — первоисточник UID для целевой инсталляции, а не `reference/`

**Контекст.** В первой версии правил мы считали `reference/metadata/system/` (выгрузка чужой работающей системы) источником UID видов и типов. Когда пользователь добавил в проект **пустую модель** через `project/metadata/`, выяснилось, что каждая выгрузка BaSYS приходит со своим `system/`, содержащим `dataTypes.json`, `kinds/` и `schemas/`. UID одних и тех же видов/типов в разных инсталляциях **отличаются** — UID — это идентификаторы строк в БД конкретной инсталляции, а не глобально универсальные имена.

**Решение.** Первоисточник UID видов, типов и JSON-схем для нашей целевой системы — **`project/metadata/system/`** (свой). `reference/metadata/system/` для UID **больше не использовать** — он подходит только как ориентир «такие типы существуют».

**Обоснование.** UID-ы, скопированные из чужой инсталляции, приведут к битым ссылкам при импорте в нашу целевую BaSYS: сервер будет искать тип/вид по UID, не найдёт, объекты не примет. Единственный корректный путь — брать UID из `system/` нашей целевой инсталляции.

**Последствия.**
- В скилле `basys-metadata` все ссылки на `../../../reference/metadata/system/` заменены на `../../../metadata/system/` (12 правок в 6 файлах).
- Шаг 11 из «Adding a New Metaobject» (запись в `dataTypes.json` при создании reference-kind объектов) — **теперь применим**: у нас есть локальный `dataTypes.json`, в который можно дописывать.
- Маленькая правка: `dataTypes.json` — единственный файл в `system/`, который мы дописываем; остальное (kinds/, schemas/) — read-only.
- В скилле специально оговорено, что **UID-ы из чужого `reference/` не использовать**, в т.ч. UID-ы из таблиц в `data-view-reports.md` и `workflows.md` (которые пришли из Cursor-rules) — обязательно сверять со своим `system/`.
- `reference/metadata/system/` теперь полностью **read-only банк примеров**: можно подсматривать структуру и схемы, нельзя брать оттуда UID.

## 2026-05-15: Имена объектов и колонок (`Name`) — только латиница snake_case

**Контекст.** В референсной выгрузке (`reference/metadata/`, БД `elevator`) часть `Name` объектов и колонок написана **кириллицей** (`акт_монтаж_ме`, `карточка_договора`, `согласование_договоров` и т.д.). BaSYS это технически допускает — в существующей системе работает. Изначальное жёсткое правило «только латиница» из удалённого `basys-knowledge-base.md` оказалось не общеплатформенным. Рассматривались два варианта: (а) принять кириллицу как допустимую и для новых объектов тоже; (б) для новых писать только латиницей, миря́сь с тем, что в `reference/` встречаются оба стиля.

**Решение.** Вариант (б): **все новые `Name` — только латиница snake_case** (`[a-z0-9_]`, длина ≤30 символов). Правило применимо к именам объектов метаданных, таблиц и колонок в `project/metadata/`.

**Обоснование.** Кириллические идентификаторы:
- Имена SQL-таблиц/полей с не-ASCII символами тянут проблемы кодировок при бэкапе/восстановлении, репликации, межсистемной интеграции.
- В URL автоформ — нужно URL-encoding, увеличивается риск багов на пограничных кейсах.
- Скрипты выражений `$h.<имя>`, `$r.<имя>` — лучше работают с ASCII-идентификаторами (меньше неожиданностей при копировании, при ручной правке в редакторах).
- Существующие объекты на кириллице работают по инерции; ставить новые на ту же траекторию — закладывать долговую мину.

**Последствия.**
- Новые объекты в `project/metadata/` — `Name` только латиницей snake_case ≤30 символов.
- `Title` и `Memo` — можно по-русски (это отображаемые/комментарийные поля, в логике системы не участвуют).
- При копировании паттерна из `reference/` объекта с кириллическим `Name` — переименовать в латиницу при адаптации.
- Это правило входит в чек-лист `.opencode/skills/basys-metadata/SKILL.md`.
- Существующие объекты в `reference/` не трогаем — это read-only корпус.

## 2026-05-16: Порядок импорта BaSYS алфавитный; перекрёстные ссылки между видами требуют явной последовательности

**Контекст.** При импорте метаданных с перекрёстными ссылками между видами обнаружено, что сервер BaSYS не строит граф зависимостей, а обходит файлы строго **алфавитно** — сначала по папкам видов (`catalog/` → `enum/` → `menu/` → `operation/` → …), внутри каждой папки — по объектам. Тип данных регистрируется только в момент импорта самого объекта; `system/dataTypes.json` — снимок, сервер на него при импорте не опирается. Если объект из более ранней папки ссылается на объект из более поздней папки, импорт всей папки одним заходом может упасть с ошибкой отсутствующего UID. Рассматривались варианты: (а) хранить только независимые партии метаданных, (б) считать такие связи ошибкой ТЗ и переписывать модель через прокси-объекты, (в) принять алфавитный порядок как платформенное ограничение и компенсировать ручной последовательностью импорта.

**Решение.** Вариант (в). Принимаем алфавитный порядок импорта как неотъемлемое свойство BaSYS. Компенсируем дисциплиной: **Инженер обязан класть в отчёт PM короткую инструкцию по последовательности импорта** в составе любой реализации ТЗ, даже когда случай тривиальный. Для случаев с перекрёстными ссылками между видами — отдельный companion-файл `<sp-id>-import-notes.md` рядом с ТЗ, с подробной последовательностью.

**Обоснование.**
- Менять платформу нельзя — мы её потребители.
- Запрещать перекрёстные ссылки между видами в ТЗ слишком ограничительно: они объективно нужны (`catalog`-объект ссылается на `enum`-классификатор — нормальная конструкция).
- Прокси-объекты или искусственные обёртки усложняют модель ради обхода ограничения импортёра.
- Знание про алфавитный порядок проверено на стенде `yuri_test` 2026-05-16; рабочий приём «удалить ссылающийся объект на сервере + повторный импорт всей папки» подтверждён, альтернатива «двойной прогон импорта» описана как менее аккуратная.

**Последствия.**
- В `.opencode/agent/engineer.md`, раздел «Specification Discipline», добавлено правило про обязательную инструкцию импорта в отчёте PM, со списком вариантов (простой случай / перекрёстная ссылка / MODIFY с новыми ссылками).
- Для нетривиальных случаев Инженер создаёт companion-файл `<sp-id>-import-notes.md` рядом с самим ТЗ.
- При проектировании ТЗ с перекрёстными ссылками Аналитик не обязан учитывать алфавитный порядок — это зона Инженера на этапе реализации.
- Если в будущей версии BaSYS появится топологический импорт — этот ADR можно будет упразднить.
