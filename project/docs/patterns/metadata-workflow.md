# Metadata Workflow Patterns

Этот документ хранит переиспользуемые выводы из прогонов. Не переносить сюда полные отчёты экспериментов; фиксировать только правила, которые реально ускоряют будущую работу.

## Рабочее Зеркало

- `metadata/` — рабочее зеркало текущего стенда BaSYS.
- Перед существенной задачей синхронизировать `metadata/` с фактическим стендом.
- После реализации импортировать/проверять изменения на стенде; PM принимает поведение системы, а не JSON-файлы.
- Не делать отдельный promotion metadata из экспериментальной папки, если PM явно не попросил изолированную ветку/worktree.

## Что Сохранять После Run

- Изменения metadata, которые стали текущим рабочим состоянием.
- Краткое ТЗ или import notes, если они нужны для дальнейшей работы.
- Новое правило/ADR/skill-правку, если run выявил устойчивый урок.

## Что Не Сохранять В Активном Контексте

- Длинные review/audit/report файлы экспериментов.
- Временные implementation plans, если они больше не управляют работой.
- Альтернативные metadata-варианты, которые не используются стендом.
- Логи рассуждений агентов.

## Уроки Из Предыдущих Прогонов

- Новые `Name` объектов и колонок — латиница `snake_case`, не SQL reserved words (`group`, `order`, `user`, `select`, `from`, `where`, `table`, `index`, `key`, `value`, `count`, `sum`, `case`, `when`, `default`).
- UID видов, типов, стандартных колонок и схем брать только из `metadata/system/`, не из `reference/`.
- `metadata/system/dataTypes.json` можно локально дописывать для reference-kind объектов, но сервер BaSYS остаётся авторитетом после импорта/экспорта.
- `manifest.json` — системный экспортный файл; не использовать его как ручной контракт реализации без явной необходимости.
- Если `menu/main` использует `AutoFill = true` для kind, новый объект обычно не нужно добавлять в меню вручную.
- Формы списка/редактирования не создавать по умолчанию. Если в задаче прямо не сказано создать формы, назначить формы или настроить UX, оставлять `ListFormUid`/`ItemFormUid = null` и использовать автоформы BaSYS. Для первой версии или чернового ядра формы не создавать. Если агент считает, что формы нужны, он сначала отдельно спрашивает PM.
- Исключение по формам: если пользователь явно просит форму списка, форму редактирования, кнопку, UX, layout, скрытие/группировку полей или удобный рабочий сценарий пользователя, тогда формы создаются через соответствующие skills.
- В workflow шаг `excel_mapping` должен использовать только primitive `DataTypeUid` (`String`, `Int`, `Long`, `Boolean`, `Decimal`, `DateTime`, `Guid`). Reference-типы (`catalog.*`, `operation.*`) в `excel_mapping` не использовать; читать Excel в промежуточные primitive-поля и преобразовывать в reference в отдельном JS/result step.
- При загрузке строк в табличную часть операции через `$t.<table>.load(source)` для каждого reference-поля передавать пару `field` + `field_display`. Например: `counterparty` и `counterparty_display`, `package_purchase` и `package_purchase_display`.
- Каждая табличная часть операции должна начинаться со стандартных колонок `id`, `object_uid`, `row_number` в этом порядке. Шаблон из референсов: `id` = `Long`, `PrimaryKey = true`; `object_uid` = `Int`, `Required = true`; `row_number` = `Int`, `Required = true`; у всех `IsStandard = true`, `StandardColumnUid = null`.
- При расчётах по регистрам не исключать текущий документ только по `object_uid`: номера разных metaobject могут совпадать. Фильтровать по паре `meta_object + object_uid`, например `NOT (meta_object = @meta_object AND object_uid = @object_uid)`.
- В workflow/script шагах BaSYS промежуточные табличные результаты, передаваемые через `_data.<step>`, возвращать как `DataTable`, а не как plain object с несколькими таблицами (`{ a: table1, b: table2 }`), если нет подтверждённого примера для конкретного механизма. Использовать методы `DataTable` из docs/reference: `.query()`, `createTable(...)`, `.addRow([...])`, `.load(...)`, `.process(...)`, `.filter(...)`, `.clone()`, `.unionAll(...)`, `.groupBy(...)`.
- При `getDisplays()` display-поля использовать осторожно: если запрос группируется, включать в `groupBy` и исходное поле, и `<field>_display` (см. `basys-docs/ru/calculations/queryBuilder.md`). Если в `where` поле может конфликтовать с полями присоединённых display-таблиц, квалифицировать имя алиасом таблицы. Подтверждённые алиасы по docs/reference: `cat_<objectName>` для `catalog`, `opr_<objectName>` для `operation`; алиасы для других видов подтверждать отдельно перед использованием как правила.
- При загрузке нескольких табличных частей операции из команды может потребоваться `await recalculate()` между `$t.<table>.load(...)`, иначе следующая таблица может примениться или отобразиться только после ручного пересчёта формы.
- Для простого catalog не запускать multi-agent; достаточно quick metadata + self-check.
- Для средних задач с известными паттернами предпочтителен single-agent autopilot: один контекст, внутреннее ревью, без persisted review/audit файлов.
- Multi-agent использовать только там, где независимый reviewer/auditor окупает стоимость.

## OpenCode Session Compaction

- В `opencode.json` зафиксированы: `compaction.tail_turns = 3`, `compaction.preserve_recent_tokens = 8000`.
- Мотив: PM-сессии с автопилотными циклами analyst → reviewer → engineer → auditor длинные; дефолт `tail_turns = 2` рискует обрезать критичный последний круг ревизии. Параметры подобраны экспериментально и подлежат пересмотру после первых длительных прогонов.
- При появлении симптомов (после компакции теряется состояние автопилота, оркестратор повторно запрашивает уже сделанные шаги) первым шагом поднимать `preserve_recent_tokens`, а не `tail_turns`.
- Источник правды по семантике полей — `https://opencode.ai/config.json` и страница `https://opencode.ai/docs/config/`.
- Долговременное состояние всё равно держать в файлах (`PROJECT_CONTEXT.md`, `OPEN_QUESTIONS.md`, `project/docs/specs/`), а не полагаться на context window.

## Read-only Защита Внешних Папок

- `basys-docs/`, `basys-cursor-rules/`, `reference/` — read-only зоны (см. AGENTS.md).
- Помимо правил permission, на запись стоит hard fallback — `.opencode/plugins/readonly-guard.ts`. Плагин блокирует `edit`, `write` и `apply_patch`, если путь попадает под один из этих префиксов.
- Плагин НЕ перехватывает `bash` (например, `rm -rf basys-docs`). Для bash полагаемся на `permission.bash` каждого агента.
- Если защита мешает легитимной операции (например, обновлению `basys-docs/` через skill `basys-docs` с явным git pull), временно отключить плагин нельзя горячо — нужно либо удалить файл, либо изменить список префиксов и перезапустить OpenCode.

## Курирование reference/

`reference/` содержит две части:

1. **Эталонный экспорт** действующей BaSYS-системы — `reference/metadata/` плюс набор индексов вида `reference/INDEX.md`, `INDEX-catalog.md`, `INDEX-operation.md` и т.д. Этот слой не курируем, не редактируем и не дополняем вручную.
2. **Курируемая копилка паттернов** — отдельные подпапки на верхнем уровне `reference/`, по одной на интересный приём. Индексируются в `reference/PATTERNS.md` (плоский каталог по бизнес-возможностям).

Перед добавлением нового metadata в курируемую копилку:

1. Найди в `reference/PATTERNS.md` категорию (бизнес-возможность), к которой относится новый пример.
2. Если категория есть и пример в ней уже присутствует — НЕ добавляй. Исключение: новый пример использует принципиально другой механизм (workflow вместо computed-column, RecordsSettings вместо JS-расчёта и т.п.).
3. Если категории нет — заведи раздел в `PATTERNS.md` и добавь пример.
4. Подкаталог именуется по доминантному паттерну, kebab-case (`reference/fifo-minutes-distribution/`), не по проекту-источнику.
5. Внутри подкаталога — обязательно `README.md` с бизнес-контекстом, плюс минимальный набор metadata-файлов, нужных для понимания паттерна. Тривиальные связанные объекты (контрагенты, единицы измерения и пр.) не копируем.
6. После создания обнови `PATTERNS.md` строкой в соответствующем разделе.

Старые объекты из эталонного экспорта индексируем в `PATTERNS.md` **лениво**: добавляем строку, когда конкретный пример из эталона реально понадобился в текущей работе. Большой ретро-аудит не запускаем.

Технический момент: `reference/` защищён плагином `readonly-guard`. Для курации используем bash-операции (`Copy-Item`, `Set-Content`, `Add-Content`, `Move-Item`) — плагин их не перехватывает.
